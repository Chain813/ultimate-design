# 地块通用化重构计划可行性与不足评估报告

## 一、 可行性评估（Feasibility Analysis）

该重构计划在**系统框架、3D数字孪生与大屏核心渲染**层面具有极高的可行性，但在 **2D规划图册与具体设计文本表达** 层面存在显著的深度耦合限制。

### 1. 核心可行项 (High Feasibility)
*   **3D数字孪生与大屏视口参数化**：主页 3D 地图（`map3d_standalone.html`）与数据大屏（`datav_bigscreen.html`）的视口（经纬度中心、Pitch、Bearing、Zoom）完全可通过 JSON 注入实现 100% 配置驱动，极易重构。
*   **空间数据路径与 CRS 解耦**：通过在 `config.yaml` 中配置 `local_crs`（如上海 `EPSG:32651` 或长春 `EPSG:32650`），并修改 `spatial_engine.py` 中的 `_project_for_geometry_ops` 函数，可以自动适配不同城市的地理投影。
*   **数据大屏静态指标统计**：大屏的用地类型 ECharts 占比、建筑高度分布频数、以及 POI 列表等，均已实现基于 GeoJSON / CSV 属性列的动态聚合计算，只要新地块数据遵循国标属性字段名即可自动渲染。

## 二、 核心不足与深度耦合限制（Shortcomings & Coupling Risks）

经过对源码的深度检索，发现现有代码中存在以下多项**地理空间与内容上的深度耦合**，这是原计划未完全覆盖的不足之处：

### 1. 2D制图脚本本质是“程序化设计插图”而非“通用渲染器” (Weakness 1)
项目 `tools/drawings/` 目录下的 20 余张图纸（如 `dr_074.py`、`dr_075.py`）为了达到毕业设计极其饱满的 A3 图册排版效果，写入了大量**特定的设计内容与硬编码坐标**：
*   **坐标与引线硬编码**：例如 `dr_074.py` 中的 5 个重点地块（“老水产市场”、“食品调料市场”等）的指引线起点、卡片坐标（如 `X: 880, Y: 300`）和对应的经纬度坐标全为硬编码。
*   **文本内容硬编码**：图纸下方的具体文字（如对于长春铁北老工业区、伊通河沿岸的文脉分析，以及特定的“吉林建筑大学”图签印章）是直接写入代码的。
*   **重构限制**：若直接更换为上海或其他城市的地块，由于地图范围与地块质心全部改变，这些特定的引线、计算卡片和长春的分析文本将直接错位、甚至指向地图视口之外，且图面语义将发生矛盾。

### 2. 空间引擎算力存在地理换算硬编码 (Weakness 2)
在 `spatial_engine.py` 的边界面积计算中：
```python
# 99: area_deg = abs(np.dot(x, np.roll(y, -1)) - np.dot(y, np.roll(x, -1))) / 2
# 100: total += area_deg * 80 * 111 * 100
```
*   `80 * 111` 是一个估算常数（在北纬 43.9° 附近，1经度≈80km，1纬度≈111km）。
*   若将地块切换到南方城市（如广州北纬 23°，1经度≈102km），此处的面积计算（容积率与绿地率测算）将会产生巨大的数学偏差。

### 3. 数据源字段名（Schema）硬编码 (Weakness 3)
算法引擎默认读取数据源中特定的列名：
*   建筑底座字段：强制读取 `"Floor"` 或 `"levels"`（如 `spatial_engine.py:L127`）。
*   用地规划字段：强制读取 `"Type"`, `"Color"`, `"GB_Code"`（如 `spatial_engine.py:L294`）。
*   街景指标字段：强制读取 `"GVI"`, `"SVF"`, `"Folder"`, `"Point_"` 等。
如果新地块的 GIS 数据来源不同（如从 OpenStreetMap 或高德直接导出的数据字段），在没有统一清洗的情况下，平台各页面会直接发生 `KeyError` 崩溃。

## 三、 针对不足的重构优化建议（Recommendations）

为了解决上述问题，建议将重构计划细化并升级为以下**三阶段过渡方案**：

```mermaid
graph LR
    L1[第一阶段: 3D视口与底座解耦] --> L2[第二阶段: 投影算法与数据Schema统一]
    L2 --> L3[第三阶段: 2D制图分级抽象与图签模板化]
```

### 1. 第一阶段：3D 沙盘与视口解耦（即可行性最高的重构）
*   先在 `config.yaml` 中提取地块名称、3D地图中心坐标与初始视口角度，在 HTML 中以占位符替换，保障数字孪生与大屏一键换地。

### 2. 第二阶段：改进空间计算数学公式
*   在 `spatial_engine.py` 中废弃硬编码的经纬度面积估算常数，统一改用 `Geopandas` 投影到本地 `local_crs` 后的几何对象投影面积计算（`.area`），或使用 `pyproj.Geod` 进行测地线（Geodesic）精确面积计算，彻底解决纬度差异带来的计算偏差。

### 3. 第三阶段：2D 制图脚本的动态重组
*   **图签配置化**：将图纸右下角的作者、指导教师、设计单位、图号从代码中移至 `config.yaml` 统一读取。
*   **分级制图策略**：
    *   **通用分析图**（如用地现状图、道路网图）：其地理要素完全动态读取 GeoJSON，视口范围通过 `boundary.total_bounds` 自动包络线居中计算。
    *   **设计策略插图**（如 `dr_074` 经济测算、`dr_039` 总体策略）：由于其强烈的设计特异性，不宜强行塞入统一配置，应在 `config.yaml` 中指明图纸渲染类型为 `generic` 还是 `bespoke`。对于 `bespoke` 类型，支持加载备用的静态插图，或在 `tools/drawings/` 下提供重写样例。
